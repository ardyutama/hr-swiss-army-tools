  • the interface becomes the test surface: pure functions, no mount
  • copy drift between list row and workspace strip becomes impossible

Problem

"What counts as saved" is dialog implementation, yet the interface exports it: the page builds, deep-copies, and re-injects a VacancyWritePayload so the dialog's watcher can reset its own baseline — and the dialog already has three payload construction paths (submit, dirty-check, watcher).

Solution

Delete the savedPayload prop and watcher; expose markSaved() next to the existing applyServerErrors(), and let the dialog snapshot its own currentFormPayload().

Wins

  • interface loses a prop, a watcher, and the deep-copy invariant
  • locality: baseline logic lives only in the dialog
  • deletion test: savedPayload removed, complexity concentrates, nothing reappears in the page
  • three payload builders collapse toward one

Deepen the vacancy-detail flow's 53-member interface

Worth exploring in-process

After — small interface, same behaviour

interface
~20 names, grouped by render region

implementation absorbs
the pass-throughs

Dialogs take v-model:open and own their open state; the earned parts stay: round pinning, permissibility rules, refresh coordination.

Problem

The extraction out of the view was the right move, but the flow module is a shallow aggregate: the view must still learn 53 names, most of them renamed re-exports of the sub-composables it wrapped. Its only caller is the view, and the seam tests mount the view — so this interface is nobody's test surface.

Solution

Push dialog open-state into the dialogs (Nuxt UI v-model:open), delete the setter pass-throughs, and group what remains around the view's render regions (rollup, rounds, candidates, import) instead of a flat bag.

Wins

  • interface shrinks by half; depth shows up as leverage for the one caller
  • deletion test: openImport/closeImport vanish, nothing reappears elsewhere
  • the flow keeps what earned it: round pinning, permissibility rules, refresh coordination
One adapter means a hypothetical seam: useVacancyDetailFlow has exactly one caller. If the view stays the test surface, consider whether the flow's interface should be shaped for the view's regions — or whether some members belong back in the sub-features.

Problem

From() grew a third optional parameter whose fallback silently recomputes the interim hiring projection (ActiveHires = 0) — harmless today, wrong-by-default the moment ticket 02 lands real hire counts. Meanwhile GetDetailsAsync stopped calling GetAsync, leaving GetAsync dead, and the module named VacancyProgress now projects summary, progress, and hiring.

Solution

Split the factory into two named constructions (new vacancy vs stored vacancy), make the stored path's inputs required, delete the dead GetAsync, and let the module name catch up with what it projects.

Wins

  • the interface states its invariant in types, not in caller discipline
  • ticket 02 can't ship a stale-zero response by forgetting an argument
  • delete dead code: GetAsync and the fallback branch

Top recommendation

Give Shortage and Filled one module

Smallest change, highest locality: the derivation is already copied three times with drifting copy, and ticket 02 (hire outcomes) — the very next slice — lands exactly on this seam. Do it before the counts become real and the copies start disagreeing about live numbers.
